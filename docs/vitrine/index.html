Un contexte territorial pour les assistants, et pour les personnes

geocontext est un serveur MCP qui sait « où l'on est » : région, département, EPCI, commune, parcelle. Il lit les données à la demande chez leur producteur, principalement sur la Géoplateforme, et les montre aussi bien à un assistant qu'à une personne devant une carte.

PrototypeLes données ne sont pas copiéesLicence MIT

Le problème de départ

Interrogé sur un lieu, un assistant produit volontiers une réponse plausible mais fausse : un zonage approximatif, un nombre de bâtiments inventé, une limite communale mal placée. Brancher directement des API géographiques ne suffit pas : leurs réponses sont volumineuses (géométries complexes, milliers d'objets) et peu adaptées à un modèle de langage.

Ce que le projet essaie de faire

Donner à l'assistant des outils qui renvoient peu de texte (comptes, statistiques, description de couche) et des valeurs autorisées plutôt que des noms à deviner.

Ce qu'il essaie de ne pas faire

Copier les données, approcher un résultat en silence, ou affirmer qu'une carte montre quelque chose sans l'avoir relu.

Aperçu

Captures de l'interface web sur la commune de Cassis (13022) et l'une de ses parcelles. Elles ont été réalisées sur une instance de test, avec les données réelles de la Géoplateforme au moment de la capture.

Une session, quatre façons d'y accéder

Le serveur maintient, pour chaque connexion, un contexte de navigation : le territoire, le thème, les données et les couches chargées. Tous les clients lisent et modifient ce même contexte.

Client MCP

Claude Desktop, Cursor ou l'Inspector se connectent en stdio ou en HTTP. Ils reçoivent sept outils dont les valeurs autorisées dépendent du contexte.

Interface web

Carte, tableaux, filtres, représentations et export. Elle parle au serveur comme un client MCP et fonctionne sans modèle de langage.

MCP App

Une carte embarquable (ui://geocontext-map) déclarée par les outils, que les clients compatibles peuvent afficher dans la conversation. Elle n'a pas été testée dans un client réel pour cette présentation.

Agent intégré

Une boucle côté serveur, avec un modèle au choix de l'exploitant (API de type « chat completions »). Elle utilise les mêmes outils et agit sur la même session que la page : ce qu'elle fait se voit à l'écran.

Principes de conception

Cinq choix, chacun avec sa raison.

1. Le contexte est l'interface

Naviguer, choisir un thème, charger une donnée : ces étapes sont les mêmes pour une personne qui clique et pour un modèle qui appelle un outil. Le contexte courant détermine ce qui est proposé ensuite.

2. Des valeurs autorisées plutôt que des noms à deviner

Sept outils, toujours listés. Leurs descriptions et listes de valeurs (thèmes, actions, couches) sont recalculées selon le contexte, ce qui limite les noms inventés. Ils ne disparaissent jamais : certains clients ne relisent pas la liste d'outils en cours de conversation.

3. Les géométries ne passent pas par MCP

Un résultat contient des comptes, des statistiques et une description de couche (service, couche, filtre, style). La page récupère elle-même les objets chez la Géoplateforme. Les réponses restent courtes, les données ne sont pas recopiées.

4. Dedans, à cheval, hors : et on le dit

Pour les couches concernées, chaque objet est classé avec sa géométrie exacte et le contour exact du territoire. Les écartés sont listés. Au-delà d'un volume contrôlable, la réponse est un refus explicite, sans total approché.

5. Afficher, relire, accuser

Le serveur ne sait pas ce qui est affiché. Une opération d'affichage est exécutée par la page, qui relit l'état réel (comptes, couches visibles) et l'accuse ; sans accusé, l'outil renvoie une erreur. Ce qu'un assistant affirme avoir affiché a été relu.

Aussi : dire ce qui manque

Une valeur absente est dite absente, un objet sans position fiable est signalé, une source injoignable donne une erreur et non un résultat vide.

Essayer

# Client MCP (stdio), après construction locale
{ "mcpServers": { "geocontext": { "command": "node", "args": ["/chemin/vers/geocontext/dist/index.js"] } } }

# Interface web
npm install && npm run build
TRANSPORT_TYPE=http npm start      # → http://localhost:3000

# Agent intégré (facultatif)
AGENT_LLM_BASE_URL=… AGENT_LLM_MODEL=… AGENT_LLM_API_KEY=…

État et limites

C'est un prototype. Voici ce qui est vérifié, ce qui ne l'est pas, et ce qu'il faudrait avant un usage plus large.

Vérifié

  • Appartenance exacte aux niveaux commune, EPCI et département, comparée à un calcul indépendant.
  • Parcelle : zonages et bâtiments comparés à un calcul indépendant sur quatre parcelles d'une commune.
  • Filtres, représentations et zone visible, joués dans un navigateur, avec relecture de la carte.
  • Tests hors réseau (registre, exécuteurs, pivot géométrique) : 58 sur 58. Les tests d'intégration appellent la Géoplateforme réelle et dépendent de sa disponibilité ; l'un d'eux (SIREN d'un EPCI du Doubs) échoue à cause de l'amont.

Non vérifié ou non disponible

  • Région : comparaison indépendante non terminée.
  • Niveau bâtiment : non navigable (refus explicite).
  • DVF : comptage seul ; SIRENE : injoignable depuis l'environnement de test ; certaines sources parcelle : erreur explicite.
  • Somme des cellules hexagonales : non relisible via la carte.
  • MCP App : non testée dans un client réel.

Avant un usage plus large

  • Authentification et gestion des droits (aujourd'hui : aucune).
  • Suivi des coûts de l'agent ; version du composant carte à figer.
  • Pas de reprise de service : dépendance aux services amont.

À ne pas en attendre

  • Aucune valeur juridique : consulter la source officielle pour tout acte (zonage, servitude, transaction).
  • Pas de recherche sémantique (recherche par mots-clés uniquement).
